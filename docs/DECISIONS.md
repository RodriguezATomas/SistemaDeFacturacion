# Decisiones técnicas

| ID | Decisión | Justificación / alternativas |
|---|---|---|
| D-01 | El alcance se toma del documento `Plan_inicio_tecnico_facturacion.pdf` y del prompt maestro | El "SPEC funcional completo" mencionado no fue entregado. Por indicación del responsable se avanzó sin consultas; los requisitos de ese documento se incorporarán a la matriz cuando esté disponible. Contradicción detectada: el PDF pide no desarrollar todo en la primera tarea y el prompt maestro pide el sistema completo; prevaleció la instrucción más reciente (sistema completo), respetando las fases del SPEC. |
| D-02 | Monorepo con npm workspaces (`apps/api`, `apps/web`, `e2e`) | Una sola versión, lockfile único, sin herramientas extra (Nx/Turborepo innecesarios para dos apps). |
| D-03 | Ramas: TEST (desarrollo), DEVELOP (integrada), MAIN (solo README) | Requisito de aceptación. La rama `main` existente se renombró a `MAIN` (en Windows, `main` y `MAIN` colisionan en el sistema de archivos). TEST y DEVELOP parten del commit inicial; MAIN nunca recibe merges. Las ramas no se publicaron en el remoto automáticamente (decisión del responsable). |
| D-04 | Aislamiento multi-tenant lógico por `companyId` validado en el servidor en cada request | Simple, auditable y probado. Row Level Security de PostgreSQL se evaluó como defensa adicional futura; requiere variables de sesión por transacción y complica Prisma. |
| D-05 | Empresa activa dentro del JWT y revalidación de membresía por request | Permite cambiar de empresa sin re-login y revocar accesos al instante. Costo: 2-3 consultas livianas por request. |
| D-06 | Refresh token opaco, hash SHA-256, cookie httpOnly SameSite=Strict, rotación con detección de reutilización | Mitiga XSS (el token de larga vida no es accesible desde JS) y robo de tokens. El access token vive en memoria. |
| D-07 | Argon2id para contraseñas | Recomendación OWASP vigente; binarios precompilados para Windows/Linux. |
| D-08 | Certificados y tickets ARCA cifrados con AES-256-GCM en la base | Evita archivos sueltos en disco y funciona igual en SaaS e instalación privada. Alternativa futura: KMS/Vault. |
| D-09 | Cliente SOAP propio (https + fast-xml-parser) en lugar de una librería SOAP genérica | Control fino del timeout, del momento de envío (incertidumbre) y del TLS que exige ARCA; menos dependencias. |
| D-10 | Lease en tabla `emission_locks` en lugar de bloqueos de sesión de PostgreSQL | El estado SENDING debe persistirse **antes** de llamar a ARCA (fuera de una transacción larga) y el lock debe sobrevivir al pool de conexiones; el lease vence solo si el proceso cae. |
| D-11 | Almacenamiento S3 vía SeaweedFS en docker compose | MinIO dejó de publicar imágenes en Docker Hub; SeaweedFS es S3 compatible y mantiene imágenes versionadas. Cualquier S3 (AWS, R2, MinIO propio) funciona configurando `S3_*`. Instalaciones privadas pueden usar disco local. |
| D-12 | Actualización de dependencias por seguridad | Se actualizaron NestJS 11.2, fast-xml-parser 5.12 (vulnerabilidad crítica), zod 4, nodemailer 10, node-forge 1.4.3, react-router 7, vite 6.4.6, vitest 5 y @aws-sdk 3.1170. `deepmerge-ts` (CLI de Prisma) se fuerza a 8.0.2 con `overrides`. Riesgo residual: glob/minimatch (moderadas) en `@nestjs/cli`, herramienta solo de desarrollo; se resolverá al pasar a `@nestjs/cli` 12. `npm audit --omit=dev`: 0 vulnerabilidades. |
| D-13 | Prisma 6 (no 7) | Prisma 7 cambia el modelo de configuración y requiere adaptadores; la migración se planifica en el ROADMAP. |
| D-14 | Selects nativos estilizados en formularios | Accesibles, compatibles con React Hook Form y livianos; Radix se usa en diálogos, menús, tabs, popovers, checkboxes y switches. |
| D-15 | `.env` del proyecto con prioridad en desarrollo | En el equipo de desarrollo existía un `DATABASE_URL` global de otro proyecto. En producción las variables del entorno siempre tienen prioridad. |
| D-16 | Pruebas de integración sin vaciar la base | Prisma bloquea `migrate reset` ejecutado por agentes de IA; las pruebas usan `migrate deploy` (no destructivo) y datos únicos por prueba en la base `facturacion_test`. |
| D-17 | Factura de exportación (WSFEX) fuera del alcance de esta entrega | El SPEC la pide "cuando corresponda". Se bloquea explícitamente la operación con clientes del exterior en lugar de emitir un comprobante incorrecto. |
| D-18 | Cobro de suscripciones administrado manualmente por el administrador de plataforma | El SPEC exige administrar planes y suscripciones, no integrar una pasarela de pagos; integrar una pasarela es una decisión comercial pendiente. |
